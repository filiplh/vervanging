# T3 Code adapter

Every T3 tool call the factory makes is in this file and the references under [`t3/`](t3/), and nowhere else. Core
skills name an operation from [`README.md`](README.md) ("runtime: `start`"); this file says how T3 does it.

Tool names below are T3's own (`delegate_task`). In Claude Code they are MCP tools named
`mcp__t3-code__<name>` and are loaded on demand, so load each one with the tool search before its first call. A tool
may load late: try the name once before calling it absent.

Facts were checked against T3 on 14 Nov 2026. [What was verified](t3/verified.md) lists which
ones were exercised and which come only from the tool descriptions.

This file holds what a normal session uses. The rest is in [`t3/`](t3/), loaded only when its trigger comes up;
each is linked below where that happens.

## Tools the factory uses

Each operation below names its tools. The full table, with the parameters the factory sets, is in
[t3/tools.md](t3/tools.md).

**Never used by the factory:**

- `t3_thread_interrupt` on a delegated child: stop it with `task_cancel`.
- `t3_thread_send` with `mode: "restart"` (it interrupts and restarts the turn), with `mode: "auto"` (it does not say
  which of start, steer or queue it chose), or with `freshContext` for `notify`.
- Sleeps, polling loops, `Monitor` or scheduled wake-ups to wait for a child or a PR. `schedule_task` is used only for
  the back-off wake (one per provider) and the night wake (one per lead), never with `type: "interval"`.
- `t3_thread_launch` or `create_threads` for ordinary children: they are `delegate_task` children. A new top-level
  thread is only a fresh lead (`launch-lead`), or the [fallback](t3/fallback.md) with the
  user's OK.
- `t3_worktree_handoff`: it moves the calling thread itself into a worktree; the lead stays in its home.
- Workflows (multi-agent scripts): only when the user asks for one.
- Any tool that writes projects (`t3_project_create`, `t3_project_update`, `t3_project_delete`).
## `check-home`: the lead lives in its project

A delegated task always runs in the calling thread's own T3 project ([the finding](t3/verified.md#check-home)).

**Rule:** a project's lead thread lives in that project's T3 project, in its **home**: the root checkout on the
default branch, or, when the root checkout is the owner's (uncommitted work, another branch), a **home worktree**: a
worktree of the same repo that is clean and whose `HEAD` is `origin/<default>`. Solo mode runs its review child the
same way, so the solo thread lives there too. Children's worktrees are made from the home's `HEAD`, so a home at
`origin/<default>` gives them the same base as a clean, pulled root checkout. The root checkout is never touched,
stashed or switched to make a home.

Check at every session start, before the first `start`:

1. `orchestrator_capabilities` (the `resolve` call) returns `parentThreadId`: the id of the calling thread.
2. `t3_thread_read` on that id with `limit: 1` gives the thread's `projectId`, `worktreePath` and `branch`.
3. `t3_project_read` on that `projectId` gives the project's workspace root. `t3_project_list` gives each project's
   `repositoryIdentity.canonicalKey`, which must be `github.com/<project.repo>` from `factory.yaml`.
4. Pass when the canonical key matches and either:
   - `worktreePath` is the project's workspace root (the root checkout); or
   - `worktreePath` is a home worktree: `git -C <worktreePath> rev-parse --path-format=absolute --git-common-dir` is the
     workspace root's `.git`, `git -C <worktreePath> status --porcelain` prints nothing, and after `git fetch origin`
     its `HEAD` equals `origin/<default>` (`git rev-parse HEAD origin/<default>` prints one commit twice). A home
     worktree on a branch of its own moves there with `git merge --ff-only origin/<default>`; it never gets commits.
     In agent-token mode `on` or `staged` ([Security](t3/security.md)) only the root checkout passes: the broker runs
     its root-only verbs (merge, labels, re-runs) nowhere else.

   Otherwise stop: tell the user the lead must be started in the project's root checkout, or in a clean worktree of
   it at `origin/<default>` (name the project), and start nothing.

Never pass `target.projectId` to `delegate_task`.

## `resolve`: providers and models, once

Call `orchestrator_capabilities` once per session, before the first `start`. Call it again only after a T3 error or
when the user names a provider change.

The result lists **provider instances**. Each has a `providerInstanceId`, a `driverKind`, `canRunChildTask`,
`canRunCrossProviderChildTask`, `constraints` and `models`. Each model lists its `options` with allowed `values` and
a `default`. The short list omits some models (`omittedModels`); `orchestrator_capabilities` with `search: "<model
id>"` finds them.

Map each model spec `<provider>/<model id>/<effort>` (from the model policy, `docs/factory-yaml.md` › `models`) to a
T3 target:

| Spec part | T3 field | How |
| --- | --- | --- |
| provider `claude` | `providerInstanceId` | the instance with `driverKind: claudeAgent` |
| provider `codex` | `providerInstanceId` | the instance with `driverKind: codex` |
| model id | `model` | must be listed under that instance's `models` (or found with `search`) |
| effort | `options: { <effort option>: <effort> }` | the model's effort option: `effort` on `claudeAgent`, `reasoningEffort` on `codex`; the value must be in its `values` |

Pick the instance by its capabilities, never by a remembered id: one machine can have several instances of a driver
(for example a disabled `codex` and an enabled `codex_2`). Usable means `canRunChildTask: true`, no `constraints`, and
the model listed. A child on another provider than the lead also needs `canRunCrossProviderChildTask: true`.

If no usable instance offers the model, or the effort is not an allowed value: tell the user which spec failed and
why (the `constraints` text), and wait. Never pick another model, provider, effort or tier (L29).

Keep the resolved table for the session. Put no instance ids in files: they are local to the machine.

## `start`: one child, explicit model and effort

### Refuse without a model and effort

`start` takes a spec and a brief. It refuses, starts nothing, and says why when:

- the work is an issue and the issue has no `tier:*` label (`factory claim` refuses it too);
- the caller passes no spec, or the spec has no effort;
- the spec did not resolve (see `resolve`).

The spec comes from the model policy: the issue's tier for builders, reviewers, validators and fix rounds, the role's
entry for the lead, hunters and planning agents, and the escalation ladder after an escalation. This file does not
choose models; it only refuses to start without one.

T3 copies the parent's settings into a child for every option left out, so a light child of a lead on a high effort
would silently run high. That is why `start` always passes the model and the effort, never "inherit".

### Same provider or another provider

| Child | Tool |
| --- | --- |
| Builder, reviewer, validator, fix round, hunter: anything that needs its own worktree, its own model or effort, or a PR | `delegate_task`, always, whatever its provider |
| A reviewer on another provider than the lead (the default pairing) | `delegate_task` with that provider's instance; T3 must report `canRunCrossProviderChildTask: true` |
| A helper inside a child (search, reading, summarising) | the provider's own native subagent tool, with the helper model from the model policy; not a T3 call and not an adapter start |

### The call

Before a builder start: the lead's home is clean and current, because the worktree starts from the home's current
commit and uncommitted edits stay out (L35). The root checkout: `git pull --ff-only`. A home worktree: `git fetch
origin`, then `git merge --ff-only origin/<default>`, and `HEAD` must equal `origin/<default>`. Take the slot first (`factory-lead` › Picking
work › Slots: the `factory` command shares only heavy slots so far, so builder and reviewer slots are counted by the
lead); `start` never runs without a slot.

```
delegate_task
  title:           "#<N> <short title>"            # reviews: "Review PR #<P>"
  role:            implementation | review | research | test | design | general
  isolation:       "worktree"
  mode:            "async"
  target:
    providerInstanceId: <resolved instance>
    model:              <model id>
    options:            { <effort option>: <effort> }
  task:            <the brief, ending with the send-report block below>
  clientRequestId: "<owner>-<name>-<N>-<role>-<attempt>"   # same id on a retry after a lost reply
```

- `isolation: "worktree"` for every child that touches files or opens a PR. `"shared"` (the lead's own checkout) only
  for a child that reads through `gh` and never touches a file.
- Leave out `target.projectId` ([check-home](#check-home-the-lead-lives-in-its-project)), `runtimeMode` and
  `interactionMode`: the child inherits the lead's modes, and T3 rejects modes above them.
- No secrets in `task`.

The result holds `taskId`, `childThreadId`, `link`, the `options` T3 applied, and `next`. Check that the applied
options show the effort you asked for. Then comment on the issue with every id a later lead needs (L26, L35):

```
started <role> on <spec> (T3 task <taskId>, thread <childThreadId>, branch <branch>)
```

The task id is for `task_status` and `task_cancel`; the thread id lets any lead read the child. When the child
finishes, its `executedModel` must equal the model asked for. A different model is a silent switch: tell the user.
When T3 reports `executedModel: null` (seen on 16 Nov 2026 for delegated review children, Claude and Codex alike),
the check can only confirm the requested spec (the target passed and the `options` T3 applied): note "executed model
not reported", and never count that as a mismatch or as a confirmation of the model that actually ran.

## `wait`, `result`, `read-child`, `continue`, `notify`, `cancel`

### `wait`

`delegate_task` answers with `next`: "Completion wakes this thread, so end your turn. Do not wait on it or poll it."
Follow `next` (L22). The child's completion arrives in the lead thread as a notification ("Delegated task "<title>"
finished") and starts a new turn.

- Never call `task_status` on a running task before its completion wakes you. If you lost track of a task (after a
  restart), check it once with `task_status`, never in a loop (L27).
- `mode: "wait"` blocks the turn; the factory never uses it for builders, reviewers or validators.
- When woken, scan everything that can move (other finished children, PRs, free slots), not only the one that woke
  you: the lead's wake scan (factory-lead › Never idle) reads each open PR and each running child's PR or issue.

### `result`

On the wake, `task_status` with the `taskId`. `workState` is `working`, `waiting_for_children` or `result_available`;
a finished turn whose child work is still running is not done. `summary` is the final report. Reading it marks it
delivered.

**A "waiting" summary is not the result.** A child that started a long run in the background ends its first turn
with "Waiting for <run>" ([`send-report`](#send-report-what-every-child-does-at-the-end)), and that turn's end is the
first completion notice, with the waiting line as its `summary`. The real report comes later, as a second completion
notice for the same task, when the run's end has woken the child and it has finished (a continuation). Do not act on
the first one: start no review, run no gate, keep its slot busy. Wait for the continuation notice; if it is late,
treat the child as one that [waits for a run](t3/late-child.md).

**A continuation notice can be lost.** The child finishes and posts its report on its PR or issue, but no second
notice reaches the lead: `task_status` still shows the waiting line as `summary`, with `latestTerminalSummary: null`.
So the PR or issue is the source of truth, not the notice: read it once per wake, whatever woke you, and act on a
report found there as on its completion.

### `read-child`

`t3_thread_read` reads any thread by id, also a child started by an earlier lead. Keep reads small:

```
t3_thread_read  threadId: <childThreadId>  view: "messages"  limit: 3  maxCharsPerItem: 4000
```

Page with `afterPosition: <nextPosition>`, or continue a cut-off item with `itemId` and `textOffset`. Use it when a
child's report seems late: the ids are in the issue's "started" comment (L26). Read once, act on what you find; never
read in a loop.

**A child whose turn ended without a report** (none on its PR or issue): [t3/late-child.md](t3/late-child.md).

An idle child never counts as a busy slot; a child waiting on a run that is still going does.

### `continue`

`t3_thread_send` to a finished child's thread starts a fresh task in that thread, with its context and its worktree,
and returns the new `taskId`.

```
t3_thread_send  threadId: <childThreadId>  mode: "queue"  message: <what to do>  clientRequestId: <unique>
```

Use it for a fix round on the same tier and for the first resume after a 403 ([`recover-403`](t3/recover-403.md)).
Comment the new task id on the issue. Do not use it for a review or a re-review: each review is a new `start`, so the
reviewer reads the change fresh. An escalated fix round is a new `start` with the higher spec.

### `notify`

An urgent message to a running child: the emergency stop's backup message, a warning before a `cancel`. Nothing else
uses it; ordinary follow-ups are `continue`.

T3's send tool has four modes. Its description: "`mode:'auto'` starts an idle thread, steers a running turn, or
queues. `queue`: new turn. `steer`: mid-turn update. `restart`: interrupt and restart. A send to a finished child
thread starts a fresh task and returns its `taskId`." `notify` uses `steer` first and `queue` (which is `continue`) as
its fallback:

```
t3_thread_send  threadId: <childThreadId>  mode: "steer"  message: <the message>  clientRequestId: <unique>
```

What the lead does in each state of the child, the result it reports, and the rules:
[t3/notify.md](t3/notify.md).

### `cancel`

`task_cancel` with the `taskId` and a short `reason`. It stops the task's running and queued turns, its own children,
and its PR watches. A finished task keeps its result. Use it when a child is replaced or no longer needed; give its
slot back afterwards.

## Pull requests and CI runs

### `link-pr` and `watch-pr`: when a child reports a PR

In the lead thread:

1. `link_pull_request` with the PR `url`: T3 shows the PR's state in the thread.
2. `watch_pull_request` with the same `url`. T3 wakes the lead on failed checks, passed required checks, new comments
   or reviews, and conflicts. Handle comments that are already there first; only later ones wake you.
3. End the turn after the watch call.

The watch stays on after each wake: never call `watch_pull_request` again on a wake. A wake is not a merge decision:
run the merge gate (`factory gate <P>`, or merge-gate.md by hand where it cannot judge). One watch per PR: never one
watcher over several PRs (L21).

Children link the PR they open to their own thread. Delegated children never watch a PR: the lead does.

**While CI is refused for billing, do not watch PRs**, and resume once it runs again:
[t3/ci-refused.md](t3/ci-refused.md).

Observed: a lead thread with a merged linked PR stayed open (not settled), so linking many PRs to the lead thread is
safe.

### `unwatch-pr`: after the merge

`unwatch_pull_request` with the `url` right after the merge. The PR stays linked. A closed, unmerged PR is unwatched
the same way.

### `watch-run`: a CI run T3 cannot watch

For a run that is not on a watched PR (the nightly run on the default branch, a manual workflow run): one background
shell command per run, so each run wakes the lead when it finishes (L21).

```
gh run watch <run-id> --exit-status        # started as a background command; its exit wakes the lead
```

Then `t3_background_wait` with that command's task id, so the thread shows as working while it runs. One command per
run, never one loop over several runs. PR checks need no `watch-run`: `watch-pr` covers them.

## Handoff to a fresh lead

When to hand off is the lead skill's rule (L23). How, in T3 (the handoff record, `launch-lead`, `relay`, why T3

## `recover-403`

A child that dies on a transient 403 from the model API: resume it once, then save its work and start a fresh child on
the same spec, without asking the user: [t3/recover-403.md](t3/recover-403.md).

## `back-off`

A child that stops on a usage or rate limit: fewer children on that provider, never weaker ones, with one recovery
record and one wake per provider: [t3/back-off.md](t3/back-off.md).

## `refresh-usage`

No T3 tool: T3 runs no Claude Code statusline, so the lead refreshes the figure with one command in its own shell,
from its home (the lead skill's Usage reserve). `<model id>` is the model of `models.helpers.search` (resolved as for
any spec; its provider must be `claude`):

```
sh .factory/bin/factory-usage refresh claude --model <model id>
```

- **What it does:** under the ledger's lock it checks the ledger (a figure already there, a recorded limit, an
  unreadable line) and its once-an-hour stamp, and claims the attempt; then it runs the claude CLI itself, one turn,
  no tools, in an empty temporary folder it makes and removes, with a 120 s timeout, and records the weekly figure it
  read live. The CLI uses its own login; nothing reads, prints or stores a credential. The rules are in
  `factory-usage --help` (refresh).
- **The result** is one line: `claude: N% recorded …` (exit 0), `claude: no refresh needed …` (exit 0),
  `claude: no refresh: …` (exit 3: a limit, or one less than an hour ago), or `claude: nothing recorded: <why>`
  (exit 1). Then ask `may-start` again. Never run it again before the time its line names.

## `night-wake`

When the machine settings set a `night` window and the lead has night work queued (the lead skill's Shifts), one
scheduled wake starts the lead at the window's start. It is the same mechanism as the [back-off wake](t3/back-off.md#the-wake-exactly-one-per-provider):
a one-shot `schedule_task` that posts into the lead thread.

```
schedule_task
  title:               "Night wake: <lead thread id>"
  schedule:            { type: "once", runAt: "<next start of the night window, in UTC>" }
  bindToCurrentThread: true
  prompt:              "Night wake: the night window starts. Run the lead skill's night steps (references/shifts.md › At night)."
  clientRequestId:     "<owner>-<name>-night-<runAt>"
```

- **One per lead thread.** Its title names the owner, so `list_scheduled_tasks` (which shows the whole project's
  tasks) tells whose it is. Never create a second one while yours exists, and never touch another thread's, except
  an orphan at session start (below).
- **`runAt`:** the next time the machine's local clock shows the window's start, converted to UTC with the machine's
  own clock, so daylight saving time is right (`date` does it). Inside the window already, the next start is the
  next night's: this window's work starts now, without a wake, and the wake is for the next night.
- **Arm** whenever night work is queued and you own no night wake: at queueing time, at session start, and inside the
  window before it ends, whenever night work stays queued, including when every start was refused (the reserve, the
  emergency stop, the caps). A wake that finds the queue empty does nothing more.
- **Remove:** `delete_scheduled_task` with its `scheduledTaskId`, when the night queue empties outside the window, or
  at a handoff.
- **Across a handoff:** the outgoing lead removes its night wake together with its back-off wakes, before
  `launch-lead` ([t3/handoff.md](t3/handoff.md) step 2). The new lead, at session start, deletes any night wake whose
  title names another thread (an orphan: the outgoing lead has already released its own) and arms its own when the
  latest status lists a night queue. The same lead after a restart finds its own and keeps it.
- At the wake the lead's rules apply unchanged: the emergency stop check, the usage reserve, the caps and the gates.

## `record`: one take of an acceptance demo flow

In the lead thread, with the app already started on its local `PORT` (the lead skill's acceptance demo, step 3).

- **`ui` flow:** `preview_open` with `target: {kind: "environment-port", port: <PORT>, path: <start path>}` and
  `reuseExistingTab: false`; keep the returned `tabId`. `preview_recording_start` on that tab, then the flow's steps
  with `preview_navigate`, `preview_snapshot`, `preview_act` and `preview_wait_for`, on that tab only and only on the
  app's local origin. `preview_recording_stop` returns the local path of the recording (T3 caps it at 50 MiB, so keep
  a flow short); then `t3_preview_close` the tab. A stop that fails or returns no file: "not recorded: <the error>".
  Never start a second recording of the same flow.
- **`command` and `http` flow:** no T3 tool. Run each step in the shell from the demo worktree, and write the
  transcript to a fresh file outside it: the command (or the request: method, URL, body) on a line starting with
  `$ `, then its full output and its exit status (or the response status, headers and body), then the time it took.
  Plain text, nothing trimmed. A step that would print the environment or a secret is not run.

Not exercised yet: the preview recording facts come from T3's tool descriptions ([verified](t3/verified.md) lists
what was).

## `send-report`: what every child does at the end

Every brief ends with this block, so a replaced lead loses nothing (L25):

```
Final report: post it as one comment on your PR (on the issue if there is no PR), with
`gh pr comment <P> --body-file <file>` or `gh issue comment <N> --body-file <file>`, then end your turn with the
same text. It ends with the line: PR <full URL>, head <SHA>, checks and reviews <state>.
Link the PR you open to your own thread. Do not watch PRs, do not start other agents, do not launch threads.
Run a command in the foreground when it fits in one call. Start a longer run (an end-to-end suite, a slow check)
with your shell tool's own background option, or with Monitor where you have it; never detached (`&`, nohup, setsid,
a subshell), because nothing tracks a detached run and nothing wakes you when it ends. A `&` inside a background
call detaches the run too: that call ends at once, and its "finished" notice says nothing about the run. You may
then end your turn with one line naming the run: "Waiting for <command>, started <time>." Its end wakes you; then
read its result, push and report. `t3_background_wait` with the run's task id is optional: it only marks your thread
as working, it does not keep your turn open or wake you. Ending your turn on a run that is detached, or on nothing at
all, is not an end state: nothing wakes you.
```

Why a background run and never a detached one: [tested 15 Nov 2026, seen again on 18 Nov](t3/verified.md#send-report).

In agent-token mode on, a Codex child posts nothing: it ends its turn with the text, and the lead posts it
([Codex children](t3/security.md#codex-children)).

A delegated child's final turn is its report to the parent, so the parent gets it through the completion and every
lead gets it through the issue or PR. A child running as a top-level thread (the fallback) also sends it to the lead
with `t3_thread_send`.
